# 审稿输出

## 用途

统一审稿发现的结构，方便合并、去重与排序。
审稿是找问题，不是证明正确；没有证据的问题不输出，没有定位的建议不成立。
只输出 JSON 数组，不写前言、后记、解释或 Markdown 代码围栏。

## Findings Schema

每条发现包含六个字段，顺序固定：

```json
{
  "severity": "S1",
  "category": "structure",
  "location": "chapters/003-章名.md:42",
  "evidence": "原文或具体证据",
  "issue": "问题描述",
  "fix": "可执行修改建议"
}
```

字段要求：

- `severity`：只能是 `S1`、`S2`、`S3`、`S4`。
- `category`：只能是九类之一：`structure`、`character`、`prose`、`consistency`、`platform`、`factual`、`format`、`causal`、`rule_boundary`。
- `location`：文件路径加行号，或「第 N 章第 M 段」这类可回查定位；不用「某处」「中间」。
- `evidence`：引用原文或给出具体证据，不写主观感受。
- `issue`：说清问题是什么、影响什么。
- `fix`：可执行方向；事实类问题只写统一方向，不写文学创作建议。

## 严重度

- **S1**：破坏主线、角色动机、世界规则或读者信任，必须优先修。
- **S2**：明显影响章节效果、留存、节奏或人物可信度，本轮要修。
- **S3**：局部质量问题，如措辞、轻微格式、局部节奏，可排期修。
- **S4**：建议项或风格微调，不阻塞发布。

严重度按影响定，不按问题出现的次数定；同一问题重复出现时合并成一条，在 `evidence` 里列代表性位置。

## 九类 category

| 类别 | 覆盖范围 |
|---|---|
| structure | 章节结构、节奏、钩子、伏笔布局、剧情循环 |
| character | 动机、行为一致性、关系阶段、配角功能 |
| prose | 语言自然度、AI 腔、句式、标点、描写 |
| consistency | 与前文、设定、角色档案的冲突 |
| platform | 目标平台的节奏、开篇、爽点与理解门槛 |
| factual | 现实事实、数字、时间、身份、引语错误 |
| format | 段落、对话格式、空行、文件结构 |
| causal | 因果链断裂、巧合救场、动机与结果不接 |
| rule_boundary | 世界规则、能力边界、信息揭露边界被越过 |

## 硬规则

1. **有证据才输出**：每条必须能定位到原文或具体设定。推测、印象、可能的隐患不写成 finding。
2. **一条一个问题**：不要把「结构差 + 对话假 + 有错字」塞进同一条；拆开分别给 severity。
3. **修法可执行**：`fix` 要能让作者知道下一步做什么，不写「加强冲突」「提升文笔」。
4. **事实类只给方向**：`consistency`、`factual`、`causal`、`rule_boundary` 的修法写「统一为某版本」「裁定一个来源」，不替作者设计剧情。
5. **严重度不虚高**：S1 只给真正动摇主线或读者信任的问题；措辞问题通常 S3/S4。
6. **合并去重**：同一根因在多个位置出现，合并成一条，在 `evidence` 列两到三处代表位置。
7. **宁可少而准**：没有把握的问题标 S4 或不出；不为凑数编造发现。
8. **只读不改**：审稿阶段不修改正文、设定或大纲；需要修复时交给写作或改写流程。
9. **平台基准可追溯**：涉及平台的判断，写清依据的是哪类平台要求；无平台信息时按通用标准，并在 `issue` 说明。
10. **输出即数据**：最终回答必须是一个合法 JSON 数组，能被直接解析。

## 检查清单

- [ ] 每条都有 severity、category、location、evidence、issue、fix 六字段。
- [ ] severity 只用 S1–S4。
- [ ] category 只用九类之一。
- [ ] location 可回查，有文件行号或章节段落。
- [ ] evidence 有原文或具体证据，不是概括。
- [ ] issue 说清影响，不是重复 evidence。
- [ ] fix 可执行，事实类没有越权写剧情。
- [ ] 同根因问题已合并，没有重复占位。
- [ ] 没有为凑数输出低置信问题。
- [ ] 最终输出是合法 JSON 数组，没有多余文本。

## 反模式

- 输出「整体不错，但有些地方可以加强」这类无定位评价。
- 把 S4 写成 S1，制造严重度假象。
- 一条 finding 里塞多个问题，无法分别处理。
- `fix` 写「重写这一段」，不说明改什么方向。
- 事实冲突只指出矛盾，不给出统一方向。
- 把审稿变成改稿，直接修改正文。
- 用 Markdown 表格、标题或代码围栏包住 JSON。
- 输出空数组时附一句「没有发现问题」，破坏可解析性。

## 输出约束

- 只输出 JSON 数组；没有发现时输出 `[]`。
- 不输出 Markdown 代码围栏、注释、尾逗号、前后说明。
- 字段顺序固定，字符串使用双引号，特殊字符正确转义。
- 不把审稿结论写进正文文件；需要落盘时由调用方决定。
- 若输入不足以判断，输出空数组或对应 S4，并在 `issue` 说明证据不足，不臆造。
